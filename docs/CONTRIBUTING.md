# 文档维护规范

本文件说明 smart-build 文档的编写要求、风格指南和维护流程，供文档贡献者参考。

## 文档结构

```
docs/

├── 01-getting-started.md        # 第一章 上手指南
├── 02-core-concepts.md          # 第二章 核心概念
├── 03-build-flow.md             # 第三章 构建流程
├── 04-example-add-board.md      # 第四章 示例：增加板卡支持
├── 05-example-add-program.md    # 第五章 示例：增加全新程序
├── 06-example-add-package.md    # 第六章 示例：增加软件包
└── CONTRIBUTING.md              # 本文件 — 文档维护规范
```

## 编写原则

### 语言与角色

- **语言**：以中文编写，技术术语保留英文原文（如 BitBake、Layer、Recipe 等）
- **角色定位**：以资深嵌入式技术专家的视角，面向有一定嵌入式开发基础的工程师
- **语气**：专业、简洁、实用，避免啰嗦的描述

### 内容要求

1. **准确性**：所有命令、路径、配置必须经过验证，确保与代码一致
2. **完整性**：每个操作步骤不能遗漏关键信息
3. **可操作性**：读者按照文档操作应能得到预期结果
4. **时效性**：当代码更新时，相关文档应同步更新

### 格式规范

- 使用 Markdown 格式，遵循 [CommonMark](https://commonmark.org/) 规范
- 章节编号采用 `X.Y` 格式（如 2.1、2.1.1）
- 代码块标注语言类型（如 ````bash`、````python`、````c`）
- 文件路径使用代码格式（如 `meta-smart/conf/layer.conf`）
- 表格用于展示结构化的对比或映射信息

### 文件命名

- 章节文件以数字前缀排序：`01-`、`02-`、...
- 文件名使用小写英文字母和连字符，不使用下划线或空格
- 文件名应简洁地反映章节主题

## 维护流程

### 何时需要更新文档

- 新增或删除了 BSP / 板卡支持
- 配方的任务名称或依赖关系发生变化
- 构建流程或命令发生变化
- 新增了重要的功能或组件
- 修复了文档中发现的错误

### 更新步骤

1. 在对应的章节文件中修改内容
2. 如果新增了章节，更新 `docs/README.md` 的目录表格
3. 提交时在 commit message 中标注 `docs:` 前缀

### 审查要点

文档变更在代码审查时应关注：

- 命令和路径是否与当前代码一致
- 新增的示例是否可以实际执行
- 是否遗漏了关联章节的更新
- 格式是否符合本规范
